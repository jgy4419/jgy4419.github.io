### 0. 리눅스 권한을 나누는 이유

1. 모든 사람이 모든 파일을 수정하지 못하도록

> 서버에는 다양한 파일이 존재한다.

- 서비스 실행 파일
- 모델 파일
- 사용자 업로드 파일
- 환경변수 및 인증 정보
- 로그 파일
- 시스템 설정 파일

**만약 모든 사용자가 모든 파일 수정이 가능하다면..?**

- 일반 개발자가 실수로 GPU 서버의 서비스 실행 파일을 삭제하거나, 다른 사용자의 파일을 수정할 수 있다.
- 또한 외부에서 서비스 계정이 탈취되더라도 해당 계정이 접근할 수 있는 범위만 피해를 입도록 제한해야됨.
- 이것을 최소 권한 원칙이라고 한다. (각 사용자와 서비스에는 업무 수행에 필요한 최소한의 권한만 부여한다.)

2. 책임 구분 : 누가 어떤 파일을 관리하는지?

> 서버에 여러 사용자가 접속했다 가정.

```plain
GPU Server
├── test          개발자 계정
├── ai-service     AI 서비스 계정
├── deploy         배포 계정
└── root           시스템 관리자
```

각 계정의 역할을 구분하면 파일의 소유권과 관리 범위를 명확하게 할 수 있다.

- `test` : 개발 및 테스트
- `ai-service` : ComfyUI 서비스 실행
- `deploy` : 배포 작업
- `root` : 시스템 전체 관리

이렇게 나누면 서비스가 실행되는 계정과 개발자가 사용하는 계정을 분리할 수 있다.

3. 장애 격리 : 한 계정의 문제가 다른 영역으로 번지지 않도록

ex. ComfyUI 서비스가 외부 공격을 받았다 가정.

- 서비스가 `root` 권한으로 실행 중이라면 공격자가 시스템 전체를 변경할 가능성이 커진다.
- 반면 `ai-service` 라는 일반 계정으로 실행 중이고, 해당 계정에 필요한 디렉터리만 접근할 수 있다면 피해 범위를 제한할 수 있다.
- 권한 관리는 단순히 파일을 읽고 쓰는 문제가 아니라 **서버 장애와 보안 사고의 영향 범위를 제한하는 방법**이다.

**`useradd` 를 사용할 때의 기준**

> 새로운 계정을 만드는 기준은 단순히 사람이 추가될 때만이 아니다. 서로 다른 권한과 역할을 분리해야 할 때 계정을 만드는 것.

1. 사람이 서버에 접속하는 경우

> 개발자 A와 개발자 B가 같은 서버를 사용한다 가정.

```plain
개발자 A -> test
개발자 B -> test2
```

- 각자 계정을 사용하면 소유권과 접속 기록을 구분하기 쉽다.
- 반대로 모두 `root` 계정을 공유하면 누가 어떤 작업을 했는지 구분하기 어렵고, 비밀번호가 유출되었을 때 피해도 커진다.

2. 서비스가 실행되는 경우

> 예시로 ComfyUI를 실행하는 계정을 별도로 만들 수 있다.

```plain
test -> 개발자가 SSH로 접속
ai-service -> ComfyUI 서비스 실행
```

- 서비스 계정을 별도로 만드는 이유는 개발자의 로그인 환경과 서비스 실행 환경을 분리하기 위해서임

서비스 계정은 아래과 같은 특징을 가진다.

- SSH 직접 로그인을 허용하지 않을 수 있음
- 일반적인 사용자 홈 디렉터리 대신 서비스 전용 경로를 사용
- 서비스 실행에 필요한 파일만 접근 가능
- 불필요한 관리자 권한을 갖지 않음

> 서비스 계정은 사람이 사용하는 계정과 달리 **프로그램이 실행되기 위한 계정**이라고 생각하면 이해하기 쉽다.

3. 여러 서비스가 서로 다른 파일을 관리하는 경우

ex. 하나의 GPU 서버에 아래 서비스가 있다고 가정.

```plain
GPU Server
├── ai-video
├── ai-image
└── ai-tts
```

- 각 서비스가 서로 다른 모델과 설정 파일을 사용한다면 계정을 분리하는 것이 보안과 운영 측면에서 유리할 수 있음
- 다만 모든 서비스마다 반드시 계정을 만들어야 하는 것은 아니다.
- 서비스가 하나이고 관리자가 한 명이며, 파일 접근 범위도 명확하다면 기존 계정과 그룹을 활용하는 편이 더 간단할 수 있다.
- 계정은 많을수록 좋은 것이 아니라, 권한을 분리할 필요가 있을 때 만드는 것이 기준임

**`chown` 을 사용할 때의 기준**

> `chown` 은 파일의 소유권을 변경하는 명령어다.

어떤 상황에서 파일의 소유자를 변경해야되나?

1. 상황1 : 서비스 계정이 파일을 수정해야 되는 경우

> ComfyUI가 다음 경로에 결과물을 저장한다 가정.

```plain
/data/ai-video/output
```

- 현재 소유권이 아래와 같다고 가정.

```plain
root:root
```

- 그리고 권한이

```plain
drwcr-xr-x
```

- 이라면 일반 사용자가 `ai-service` 는 해당 디렉터리에 파일을 생성할 수 없다. (디렉터리에 쓰기 권한이 없기 때문)
- 이때 서비스 계정이 해당 디렉터리를 관리하도록 소유권을 변경할 수 있다.

2. 상황2 : 다른 계정이 만든 파일을 인수받은 경우

> 관리자 계정으로 파일을 생성했는데, 이후 서비스 계정이 해당 파일을 관리해야 할 수 있다.

```plain
root가 파일 생성
        ↓
ai-service가 파일 관리
        ↓
소유권 변경 필요
```

- 이때 `chown` 을 사용할 수 있다.
- 하지만 단순히 파일을 읽거나 실행하기만 한다면 반드시 소유권을 변경할 필요는 없다.
- 그룹 권한이나 읽기 권한을 부여하는 방법으로 해결할 수도 있다.

3. 상황3 : 새 서버를 구축하거나 서비스를 이전하는 경우

> 새 Linux 서버에 기존 GPU 서버의 파일을 복사했다 생각.

- 파일을 복사하는 방법에 따라 소유권이 달라질 수 있음.
- 파일이 `root` 소유로 복사되었는데, 실제 서비스는 `ai-service` 계정으로 실행된다면 파일 접근 문제가 발생할 수 있다.
- 이때 파일의 소유권을 서비스 계정에 맞게 변경할 수 있다.
- 여기서도 무조건 `chown -R` 을 실행하는 것이 아니라, 어떤 파일과 디렉터리를 서비스 계정이 관리해야 하는지 먼저 구분해야 된다.

**실제 권한을 설정할 때 어떤 기준으로 판단?**

> 리눅스 권한을 설정할 때는 아래 순서대로 생각하기.

권한 설정 판단 순서

1. **누가 이 파일을 사용하는가?** : 개발자, 서비스 계정, 관리자 중 누구인가
2. **무엇을 해야 하는가?** : 읽기만 하는가? 수정하는가? 실행하는가?
3. **어떤 범위까지 필요한가?** : 파일 하나인가? 특정 디렉터리인가? 하위 전체인가?
4. **다른 사용자에게도 권한이 필요한가?** : 특정 그룹만 접근하면 되는가? 모든 사용자에게 공개해야 하는가?
5. **서비스가 중단되거나 파일이 변경되어도 괜찮은가?** : 운영 설정이나 모델 파일처럼 보호해야 하는 파일인가?

**자주 사용하는 권한 기준**

| 대상 | 일반적인 권한 | 이유 |
| --- | --- | --- |
| 일반 설정 파일 | `644` | 소유자만 수정 |
| 비밀 설정 파일 | `600` | 소유자만 읽고 수정 |
| 실행 스크립트 | `755` 또는 `750` | 실행 권한 필요 |
| 일반 디렉터리 | `755` 또는 `750` | 접근 범위에 따라 결정 |
| 개인 파일 | `600` | 다른 사용자 접근 제한 |
| 공유 디렉터리 | `2770` 등 | 그룹 단위로 관리 |

- 위 기준은 절대적인 규칙이 아니라 일반적인 출발점이다.
- ex. 공개되어도 되는 설정 파일은 `644` 로 설정할 수 있지만, API 키나 비밀번호가 포함된 `.env` 파일은 `644` 로 설정하면 안 된다.

```plain
-rw-r--r-- .env
```

- 이 권한은 다른 사용자도 파일을 읽을 수 있다는 의미다.
- 비밀 정보가 들어 있다면 일반적으로 아래처럼 제한.

```plain
-rw-------  .env
```

- 소유자만 읽고 수정할 수 있다.

**하면 안 되는 권한 설정**

> 이제 실제 운영에서 특히 조심해야되는 것들

1. 모든 파일을 `777` 로 설정하기

```plain
chown -R 777 /data/test
```

> 위 명령은 해당 경로의 모든 파일과 디렉터리에 모든 사용자가 읽기, 쓰기, 실행할 수 있는 권한을 부여한다. 이렇게 되면..

- 다른 사용자가 파일을 수정하거나 삭제할 수 있음
- 실행 파일이 변조될 수 있음
- 모델 파일이나 서비스 설정이 변경될 수 있음
- 공격자가 서비스 계정을 통해 파일을 변경할 수 있음

> 권한 문제가 발생 시 `777` 을 설정하면 일시적으로 해결되는 것 처럼 보일 수 있지만. 실제 문제를 해결한 것이 아닌 보안 경계를 없앤 것. **권한 오류가 발생하면 777부터 적용하지 말고, 어떤 계정에 어떤 작업을 수행하려는지 확인해야됨**

2. 운영 서버의 전체 경로에 무작정 `chown -R` 적용하기

```plain
sudo chown -R test:test /data
```

- 이 명령은 `/data` 아래의 모든 파일과 디렉터리를 `test` 소유로 변경한다.
- 그런데 `/data` 에는 여러 서비스가 존재할 수 있다.

```plain
/data
├── test
├── database
├── backup
└── other-service
```

> 이런 구조에서 전체 소유권을 변경하면 다른 서비스의 파일 소유권까지 바뀔 수 있다.
> 특히 아래와 같은 경로는 무작정 변경하면 안됨.

- `/`
- `/etc`
- `/usr`
- `/var`
- `/data` 전체
- 다른 서비스가 관리하는 디렉터리

실제 변경이 필요하다면 먼저 대상 경로와 소유권을 확인하고, 변경 범위를 최소화 해야 함.

3. 서비스를 `root` 로 시작하기

- 서비스를 `root` 로 실행하면 권한 문제가 적게 발생할 수 있다.
- 하지만 이건 좋은 해결 방법은 아니다.
- 서비스가 침해되거나 프로그램에 취약점이 있다면 공격자가 관리자 권한으로 시스템을 변경할 수 있기 때문.
- 가능하다면 서비스 전용 계정을 만들고 필요한 파일에만 권한을 부여.

4. 디렉터리의 `x` 권한을 무시하기

> 디렉터리에서 `x` 는 내부 경로를 탐색할 수 있는 권한이다. 예시로

```plain
/data/test/models
```

- 에 접근하려면 `/data`, `/data/test`, `/data/test/models` 각 경로에서 필요한 탐색 권한이 있어야된다.
- 하위 디렉터리의 권한이 충분해도 상위 디렉터리에서 접근이 차단되면 파일에 접근할 수 없다.

**GPU 서버를 기준으로 권한 설계해보기**

```plain
/data/ai-video/
├── models/
├── workflows/
├── output/
├── logs/
└── config/
```

- `models/` : 서비스 계정은 읽기, 관리자는 수정
- `workflows/` : 서비스 계정은 읽기, 개발자는 수정
- `output/` : 서비스 계정이 생성 및 삭제 가능
- `logs/` : 서비스 계정이 기록, 관리자는 확인
- `config/` : 서비스 계정은 읽기, 관리자만 수정.

> 이렇게 설계하면 서비스 계정이 모델 파일을 임의로 변경하거나 설정 파일을 수정하는 것을 제한할 수 있다.

> 물론 실제 ConfyUI 는 모델을 읽기만 하는 경우도 있지만, 캐시나 임시 파일을 생성하는 경로가 있을 수 있으므로 서비스의 실제 동작을 확인해야됨.

**그룹을 활용하면 더 유연하게 관리 가능**

ex.

```plain
사용자
├── test
└── ai-service

그룹
└── ai-team
```

> 두 계정을 `ai-team` 그룹에 포함시키면 그룹 권한을 통해 파일을 공유할 수 있다.

```plain
/data/ai-video/workflows
```

- 이 디렉터리를 그룹 소유로 설정하고 그룹에 쓰기 권한을 부여하면, 그룹에 속한 사용자들이 함께 파일을 관리할 수 있다.
- 이때 디렉터리에 `2770` 권한을 사용하는 방식도 있다.

```plain
drwxrws---
```

- 앞의 `2` 는 SetGID 라는 특수 권한이다.
- 디렉터리에 SetGID 가 설정되면 일반적으로 그 안에서 새로 생성되는 파일과 디렉터리가 부모 디렉터리의 그룹을 상속하게 된다.
- 따라서 여러 사용자가 같은 그룹으로 파일을 관리할 때 유용.
- 그룹 권한을 사용해도 모든 사용자가 모든 파일을 수정할 수 있도록 설정할 필요는 없다.

**실제 서버에 권한 문제가 발생 시 아래 순서로 확인하는 습관 들이기**

```plain
# 1. 현재 로그인 사용자
whoami

# 2. 사용자와 그룹
id

# 3. 파일 및 디렉터리 소유권
ls -ld /경로

# 4. 경로의 각 디렉터리 권한
namei -l /경로/파일

# 5. 서비스 실행 계정
systemctl show 서비스명 -p User -p Group
```

### 1. `useradd` - 사용자 계정 생성

> `useradd` 는 리눅스에 새로운 사용자 계정을 만드는 명령이다.

```plain
# test라는 사용자를 생성한다는 의미
sudo useradd test
```

- 기본 설정에 따라 홈 디렉터리가 자동 생성되지 않을 수 있다. 일반적으로 다음처럼 생성하는 것 추천.

```plain
sudo useradd -m test
```

| 옵션 | 의미 |
| --- | --- |
| `-m` | 홈 디렉터리 경로 생성 |
| `-d` | 홈 디렉터리 경로 지정 |
| `-s` | 로그인 셸 지정 |
| `-g` | 기본 그룹 지정 |
| `-G` | 추가 그룹 지정 |

**예시**

```plain
sudo useradd -m -s /bin/bash test
```

생성 후 계정의 비밀번호를 설정하려면

```plain
sudo passwd test
```

- 비밀번호를 설정하면 해당 계정으로 로그인할 수 있는 준비가 된다.
- 사용자 확인은 아래처럼.

```plain
id test
```

- 예시 결과

```plain
uid=1001(test) gid=1001(test) groups=1001(test)
```

- `uid` : 사용자 ID
- `gid` : 기본 그룹 ID
- `groups` : 사용자가 속한 그룹 목록

> 리눅스는 사용자 이름뿐 아니라 숫자로 된 UID와 GID를 이용해 권한을 관리한다.

### 2. `chown` - 파일 및 디렉터리 소유자 변경

> `chown` 은 파일이나 디렉터리의 소유자(User)와 소유 그룹(Group)을 변경하는 명령이다.

- 기본 문법

```plain
chown [옵션] 사용자:그룹 파일경로
```

- ex1, 소유자만 변경

```plain
sudo chown test test.txt
```

> `test,txt` 의 소유자를 `test` 로 변경

- ex2. 소유자와 그룹 변경

```plain
sudo chown test:test test.txt
```

> 소유자 : test, 소유 그룹 : test 둘 다 변경하는 명령어다.

- ex3. 디렉터리 내부까지 변경

```plain
sudo chown -R test:test /data/test
```

- 여기서 `-R` 은 Recursive, 즉 재귀적으로 적용한다는 뜻.
- `/data/test` 디렉터리뿐 아니라 그 안에 있는 파일과 하위 디렉터리까지 소유자를 변경함.
- 주의할 점은 운영 서버에서 `-R` 을 사용할 때 경로를 정확히 확인해야 한다는 것임. 잘못된 경로에 적용하면 많은 파일의 소유권이 한꺼번에 변경될 수도 있다.

### 3. 리눅스 권한 해석 방법  `ls -l`

**예시 결과**

```plain
-rw-r--r-- 1 test test 1024 Nov 26 test.txt
```

- `-`는 일반 파일이라는 뜻이고
- 처음 `test`는 소유자. 이후 `test`는 소유 그룹을 뜻한다.

**권한 문자열을 총 10자리로 구성된다.**

| 위치 | 의미 |
| --- | --- |
| 1번째 | 파일 종류 |
| 2\~4번째 | 소유자 권한 |
| 5\~7번째 | 그룹 권한 |
| 8\~10번째 | 기타 사용자 권한 |

**첫 번째 문자는 파일 종류를 나타낸다.**

| 문자 | 의미 |
| --- | --- |
| `-` | 일반 파일 |
| `d` | 디렉터리 |
| `l` | 심볼릭 링크 |

### `r`, `w`, `x` 권한의 의미

- `r` : Read - 읽기 (파일 내용을 읽거나 디렉터리 목록을 확인. `4` 로 표시)
- `w` : Write - 쓰기 (파일 내용을 수정하거나 디렉터리 내 항목을 변경한다. `2`로 표시)
- `x` : Execute - 실행 (파일 실행 또는 디렉터리 접근. `1` 로 표시)

**권한 숫자는 각 권한의 값을 더해서 계산한다.**

| 권한 | 계산 | 숫자 |
| --- | --- | --- |
| `---` | 0 | 0 |
| `--x` | 1 | 1 |
| `-w-` | 2 | 2 |
| `-wx` | 2 + 1 | 3 |
| `r--` | 4 | 4 |
| `r-x` | 4 + 1 | 5 |
| `rw-` | 4 + 2 | 6 |
| `rwx` | 4 + 2 + 1 | 7 |

- 예시로

```plain
chown 755 test.sh
```

위 명령은 아래와 같은 권한을 설정한다.

- 소유자 : `rwx` -> 읽기, 쓰기, 실행
- 그룹 : `r-x` -> 읽기, 실행
- 기타 : `r-x` -> 읽기, 실행

즉, `755` 는 `rwxr-xr-x` 와 같은 의미이다.
`chmod` 는 권한 자체를 변경하고, `chown` 은 소유자와 그룹을 변경한다는 차이가 있다.

### 5. 디렉터리 권한은 조금 다르게 해석해야 된다.

> 파일과 디렉터리에서 `r, w, x` 의 의미가 약간 다른다.

| 권한 | 일반 파일 | 디렉터리 |
| --- | --- | --- |
| `r` | 파일 내용 읽기 | 파일 목록 확인 |
| `w` | 파일 내용 수정 | 파일 생성, 삭제, 이름 변경 |
| `x` | 파일 실행 | 디렉터리 내부 접근 및 경로 탐색 |

- 특히 디렉터리에서 `x`가 중요하다.
- 예시로 `/data/test` 에 `r` 권한이 있어도 `x` 가 없으면, 디렉터리 목록을 확인할 수는 있어도 내부 파일에 접근하지 못할 수 있음.
- 디렉터리 내부의 파일을 삭제할 때는 일반적으로 해당 파일의 쓰기 권한보다 부모 디렉터리의 쓰기와 실행 권한이 중요하다.

### 6. 실제 GPU 서버에 권한 확인하기

**ComfyUI 서버로 예시**

1. 먼저 서비스가 실행되는 계정을 확인

```plain
systemctl show comfyui.service -p User -p Group
```

2. 실제 파일의 소유권을 확인한다.

```plain
ls -ld /data/test
ls -l /data/test
```

3. 특정 파일의 권한을 자세히 확인하려면

```plain
stat /data/test/test.txt
```

결과 예시

```plain
Access: (0644/-rw-r--r--) Uid: (1001/test) Gid: (1001/test)
```

결과를 해석하면

- 권한 644\`
- 소유자 : test
- 그룹 : test
- 소유자만 파일 수정 가능
- 그룹과 기타 사용자는 읽기만 가능

> 만약 `ComfyUI` 서비스가 `test` 계정으로 실행되고 있고, 해당 계정이 파일을 수정해야 한다면 소유권을 확인해볼 수 있다.

```plain
sudo chown test:test /data/test/test/txt
```

> 하지만 운영 중인 서버에서는 무조건 `chown` 을 실행하기 보다는, **현재 서비스 실행 계정과 파일 소유자가 일치하는지 먼저 확인**해야된다.

### 7. 자주 사용하는 명령어 정리

| 명령어 | 의미 |
| --- | --- |
| `useradd -m test` | 사용자 생성 및 홈 디렉터리 생성 |
| `passwd test` | 사용자 비밀번호 설정 |
| `id test` | 사용자 UID,GID, 그룹 확인 |
| `ls -l` | 파일 권한과 소유자 확인 |
| `ls -ld 경로` | 디렉터리 자체의 권한 확인 |
| `chown test 파일` | 파일 소유자 변경 |
| `chown test:test 파일` | 소유자와 그룹 변경 |
| `chown -R test:test 경로` | 하위 파일까지 소유권 변경 |
| `chmod 755 파일` | 권한을 755로 변경 |
| `stat 파일` | 파일 권한과 소유권 상세 확인 |

**기억하면 좋은 핵심**

- `useradd` -> 계정 생성
- `chown` -> 파일 소유자를 바꿈
- `chmod` -> 파일의 접근 권한을 바꾼다
- `rwx` -> 읽기, 쓰기, 실행 권한이다.
- `755` -> 소유자는 모든 권한, 나머지는 읽기 권한이다.

>  서버 관리에서는 `ls -l` 결과를 보고 누가 소유하고 있는지, 어떤 그룹인지, 어떤 권한이 있는지를 읽을 수 있으면 기본적인 권한 분석은 할 수 있다.
